## 实施次序与交付

### 6A：先建立可比较的质量基线

1. 只读整理两个现有项目的执行、交付、主动沟通、候选、记忆与费用回执；保留原历史，记录不可观测项，不把缺失值填成成功或零费用。
2. 在隔离项目中准备开发、研究、数据/自动化三类任务，每类首批 4 个案例。各类累计至少 10 轮有明确任务变化的真实交互，覆盖初次交付、修正、插话和继续；失败、重试、模型/API 请求数另列，不能用一次工具调用算一轮用户交互。
3. 冻结输入、版本、模型/供应商、工具权限、用例分区及费用上限。先小批验证协议与环境，再执行完整批次；已经达到任务终态的案例不人为续聊凑轮次。
4. 产物验收按领域执行：开发检查运行、核心操作、控制台、桌面/窄屏视觉；研究核对来源是否支持结论、时间窗口、事实与推断区分；数据/自动化核对结果、幂等、失败核对和恢复。
5. Pi 对照执行/插话/长上下文/同条件缓存；Harness 对照交付预览与成果可达性；Headlong 对照无 Goal 状态驱动、静默与唤醒。固定参考提交与实际配置，不把不同模型或不同权限下的差别归因于 SDK。

交付：可复跑场景清单、原始结果索引、失败分层与优先级。完成这一批后才决定具体 SDK 改动及效应门槛，不预先大改提示词或重写已通过的模块。

### 6B：根据基线修复核心问题，可并行三条工作线

评测 SDK 另有已经确认、无需等新故障才立项的能力缺口：当前匿名裁判只有截图元数据，不能评价实际视觉；冻结来源的哈希/日期/引文检查不能判断结论是否受支持；本地协议夹具不能证明真实 MCP 或外部工具适配可用。需要补充匿名视觉产物审阅、逐项结论与证据对应的核验，以及选定工具的受控真实集成场景。保持双方相同环境，区分人工审阅、模型裁判与确定性检查，不能把自动评分当独立事实。扩展见 [SDK 评测执行器](../../packages/sdk/src/project-evolution.mjs)与[领域适配器](../../packages/sdk/src/project-evaluation-domains.mjs)。这部分与有效自进化工作线一起交付。

| 工作线 | 开发与实验内容 | 验收证据 |
|---|---|---|
| 主动协作与记忆 | 检查进行中/已完成/周期交付/等待用户/失败等状态转换；处理新的目录变化；核对用户纠正与 OpenViking 检索；压缩后保留承诺、权限及未完成项 | 没有 Goal 也能基于新证据行动；已交付且无变化时安静；不遗漏用户输入或到期任务；分层检索实际回执、纠错和跨项目隔离 |

三条工作线都以已经复现的缺陷为改动入口。已完成的机制重点补验证，只有出现可重复的缺口才调整代码；不强制读取所有技能来制造“生效”，不通过降低门槛或增加主动消息来提高数字。

自进化评测保留 development / selection / confirmation 分区；确认用例在候选生成前冻结并预审，发起确认即消费，失败或重试也不能复用。这里的“固定确认集”是单次实验固定，不是同一批隐藏题永久反复筛选。确认不足时准备新独立任务并如实标注，不能降为只跑筛选后宣称通过。

版本采用率只作为漏斗诊断。必须同时记录实际改动触达、通过检查的交付、任务收益、旧能力回归与总费用；未测出收益就保留“实验性/未证实”结论。
