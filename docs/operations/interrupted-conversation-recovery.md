# 中断后的对话恢复

Rna 将会话执行日志作为模型上下文的事实来源，工作台状态作为界面投影。服务重启不意味着工具已经回滚；已保存的用户消息也不能因旧工具缺少回执而永久丢在失败轮次中。

## 文件操作

`project_write`、`project_edit` 在提交文件前，先将相对路径、修改前后的完整文件 SHA-256 写入同一持久日志。能力注册器及宿主包装器传递执行上下文，检查点不是模型可修改的参数。

恢复时只读取当前文件，遵守原工作区边界、私有路径、符号链接及文件大小限制，不重新执行旧写入：

- 当前完整内容匹配目标哈希：记录当前已具备预期内容；不推断是哪次进程完成的写入。
- 当前内容不同、文件不存在，或者旧日志没有检查点：记录当前哈希和可验证的文本匹配情况，以中断结果结束旧调用。模型收到明确说明：历史结果未知，先读取当前内容，再依据最新用户要求决定新的操作。
- 文件不可读取或范围已撤销：仍保留未决状态，不伪造成功。

这只适用于可观察的本地文件操作。命令、远程 MCP 等外部效果没有通用的自动核对方法。

## 对话与交互

恢复前，用户排队的引导消息先进入 SDK 的持久队列。新的用户要求可以取消没有任何派发意图记录的旧调用；已经开始的调用必须经过核对。恢复后的新请求不重复添加原用户消息。

对已开始但没有结果的只读或声明幂等调用，新的用户要求可以结束旧调用并保留“历史结果未知、未重放”的错误回执，随后按新要求继续。要求进程清理或显式核对的调用不适用这一处理，避免出现界面没有待核对项、底层却始终阻塞的状态。

仍无法确认的调用让轮次保持“等待核对”，界面提供原始操作参数及三个结论：已完成、确认未执行、结束旧操作但保留结果未知。用户必须填写核对依据；结论通过正式会话 API 与 SDK 记录，而不是手工修改 JSONL。结束未知操作不宣称回滚，也不自动重放该操作。

失败的真实轮次提供“重试请求”，保留原轮次 ID、原用户消息、失败记录及重试历史。后续普通聊天仍可继续，新的消息不会因为恢复失败而消失。

前台聊天现选择 SDK 的 `stepLimitBehavior: 'yield'`：每 64 个模型步骤在完整工具批次后持久保存分片收据，交回调度器再自动接续同一轮，不再要求用户点击“继续”，也不生成假的用户指令。原队列只认领一次，已完成工具不重放，费用和 token 限额持续累计；取消、预算不足、未知工具效果和真正请求失败仍按各自语义停止。旧历史中的 `step_limit` 错误和显式 error 策略继续显示“继续请求”，保留真实事故证据。分片协议与 SIGKILL 恢复测试。

前台调度使用 `setImmediate` 让出 I/O，但暂停、停止、归档与急停在状态通知时同步使执行失效。记忆检索期间的新插话在原始 prompt 的第一次请求之前持久入队；每次请求前再次检查最新队列。项目主动消息以独立条目送达当前对话，之后作为有界、具名参考上下文进入前台模型，便于理解用户对它的回应；不是新的授权或伪造用户命令。已撤销或删除的内容不再进入该投影。

主动提问同样可以在前台长任务中以非阻塞交互卡送达。待答问题不等于用户已作选择；回答和取消由原交互服务持久化，下一次前台请求收到真实回答的结构化投影，按已保存权限执行。投影保留每题全部选中选项及 schema 允许的 4,000 字自填答案，不用短摘要剪掉末尾约束；有界窗口先淘汰旧记录并标记覆盖范围。权限卡仍单独通过原服务校验，普通方向选择不会自动扩大权限。见主动通信与写入交接。

恢复按钮在 SSE 状态刷新期间保持 DOM 节点和按下状态，提交时显示忙碌反馈并阻止重复请求。隔离浏览器验证使用真实按下、SSE 刷新、松开顺序：旧版按钮被卸载，HTTP 请求数为 0；修复后为 1。该证据证明界面竞态存在，不代表已确认用户每一次点击无效的唯一原因。

## 监督与边界

监督器同时检查 HTTP 健康与独立 IPC 主循环活动。只有进程身份、代次、序号、发送和接收的单调时间均通过检查，而且确有在途工作时，短暂 HTTP 不可达才暂缓终止。HTTP 降级仍进入健康报告。事件循环冻结、失效心跳、身份错误以及其他资源限制仍按原机制处理。

若旧健康请求开始时仍有工作、超时时工作刚结束，则针对这一转换重新检查一次；只有新检查通过才恢复健康，持续失联仍会触发恢复，空闲心跳不能无限延长宽限。

测试包括在真实 Node 子进程中于文件提交前或提交后、结果回执前发送 SIGKILL；随后重新打开日志并核对文件，不重放写入。受控模型协议集成测试验证新的指令能继续写文件，以及外部命令须通过交互核对。这些测试验证恢复契约，不是 100 小时运行或模型质量证明。

2026-09-25 的恢复调查另复现后台连续微任务使定时器延迟的缺陷。调度通过 `setImmediate` 让出 I/O 和心跳机会，仅在准入通过、实际复查前生成完整对话快照；权限撤销和新证据仍同步打断。隔离 500 次连续结果实验中，心跳从全部完成后才运行变为第 1 次后就运行。性能审计不将受控实验等同于生产曾发生 500 次循环。

现有 14.35 MB 会话日志的副本基准中，会话打开与回放约 235 ms，隔离运行时创建约 265 ms，没有复现数十秒停顿。副本使用临时工作区，初始化读取经过隔离，不能证明原环境的每一个 await 均正常。旧生产进程未捕获有效栈，当前仍不能将其停顿唯一归因于日志大小或调度；后续真实恢复结果另行保存。

后续定位到原生 LaunchAgent 的 `Background` 资源节流，并改为适用于即时 HTTP 工作台的 `Interactive`。实际恢复保留原轮次及已认领的调整，五分钟 58 次检查均健康，54 次模型响应、53 个新工具回执，未重放旧工具。期间临时暂停后台推进，并于结束后恢复原设置；这证明本次接续，不是前后台并发或长期稳定性验收。部署、系统级对照与失败历史见交付记录。
