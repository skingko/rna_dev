# 本地记忆（内置）

0.73.0 起，记忆有两种方式，在「设置 → 记忆」里二选一：

| | OpenViking 语义记忆 | 本地记忆（内置） |
| --- | --- | --- |
| 需要 | Docker、OpenViking、向量模型、文本模型（见 [部署说明](openviking-local.md)） | 什么都不需要 |
| 检索 | 按语义：换一种说法、换一种语言也能找到 | 按关键词：只找得到用了相同词语的内容 |
| 对话记忆 | 由模型提炼成长期记忆 | 原样保存每一段对话，不调用模型 |
| 数据位置 | OpenViking 服务的数据卷 | 本机 `<state>.rna/memory/embedded.sqlite` |

两种方式各自保存自己的记忆，互不迁移；切回原来的方式后，原有记忆仍在。配置项是 `memory.backend`（`openviking` 或 `embedded`），命令行为 `./rna memory-config --backend embedded`。0.6 之前的 `local` 是另一套已退役的记录，仍然只保留为归档，读入时按 `openviking` 处理。

## 它做什么

内置引擎（`prototypes/control-center/embedded-memory.mjs`）在主机进程内回答主机发给 OpenViking 的同一组请求，所以自动引用、记忆工具、记忆浏览、同步队列、删除会话和回退都走原来的代码，没有第二条路径。

- **文件**：交付资料、笔记、执行资料按 `viking://` 地址保存，与 OpenViking 方式的地址一致。
- **对话**：一轮结束后提交的那段对话成为一条“事件”，内容就是这段对话自己的文字，标题取用户的第一行。事件属于提交它的上传会话，删除会话时一并删除，被删的对话不会继续被搜到。
- **检索**：SQLite FTS5 的 `bm25`。英文和数字按词，中日韩文字按相邻两字切分（mu `store.ts`、zcode `read-session-context.ts` 的做法；SQLite 自带的分词器对一整段汉字只给一个词）。命中时返回文件里查询词最密集的一段原文。
- **目录的摘要与概览**：列出目录里有什么（OpenViking 在没有模型时的做法，`tiers.py`）。

它不做的事：不理解同义词和改写，不跨语言，不从对话中提炼结论。这些是 OpenViking 方式里向量模型和文本模型的工作。

## 实测

`prototypes/control-center/benchmark/embedded-memory-replay.mjs` 把一份真实状态里的对话按发生顺序重放：每一轮先用用户这句话检索（自动引用在一轮开始时就是这样做的），再把这一轮存入。只读，不写入任何状态。2026-10-10 在线上状态上的结果（112 轮、6 个对话、100 次检索）：

| 指标 | 结果 |
| --- | --- |
| 排在第一的是同一对话里更早的一轮 | 90% |
| 前五条里有同一对话里更早的一轮 | 98% |
| 把同样的问题拿去问别的对话，仍然有结果返回 | 98% |
| 存入一轮并检索一次 | 约 2.7 毫秒 |

第三行说明关键词检索只负责排序，不负责判断“记忆里有没有相关内容”：两段同一种语言的文字几乎总有共同的词。试过用查询词的覆盖率或逆文档频率加权的覆盖率设门槛，相关与不相关的分布大面积重叠（门槛取到能挡住三分之二无关结果时，也挡掉了近一半相关结果），所以没有设。这与 OpenViking 方式一致：主机对两种方式都是取分数最高的若干条，装进本轮的记忆预算（默认 2048 token）。一轮是否需要引用记忆，仍由 JEV 在检索之前判断。

样本只有 6 个对话，结论是“排序可用”，不是精确的召回率。

## 运行与限制

- 需要 Node 自带的 `node:sqlite`（随应用分发的 Node 22.19 运行时已包含；自行启动服务时用 Node 22.13 或更高）。
- 数据库文件在 `<state>.rna/` 内，随恢复点一起备份和还原。
- 健康检查中向量模型与文本模型显示为“未使用”，语义质量为 `keyword_only`。
- 另一个程序写的或更新版本写的数据库文件不会被改写，记忆操作会报错而不是覆盖。
