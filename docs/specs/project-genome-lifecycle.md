# 项目能力版本与执行边界

更新：2026-09-24。本文描述本次 Rna 实现的契约；上游来源和新增设计分开列出。

## 来源与取舍

- Pi 固定提交 a328aa89 的 agent-loop.ts 在请求边界准备模型和上下文，完整执行工具批次后再处理 steering/继续，截断的工具调用不执行。Rna 保留请求边界的能力重建、稳定系统前缀、明确的消息/工具結果配对与持久化队列。更改模型、提示词或工具 schema 会改变对应缓存前缀，不能宣称版本切换仍保持原缓存命中率。缓存计数采用提供商报告。
- Harness 固定提交 46a7f68b 的 cordis-host-runner 用不可变包区分当前执行与下一版本，定义、执行和更新有不同的提交点；agent-preset-registry 的已有实例保持既定组合。Rna 将这个原则落实为轮次固定 projectVersionId，版本选择只影响下一轮。
- Harness 的 tool-cordis 要求先检查真实运行 API/schema 再写扩展；Rna 为生成脚本提供明确的输入 schema 和受限文件 API，并实际执行 smokeCases。该提交的 goal / tool-ralph 文档明确尚无独立 evaluator，不能把本次新增评测器描述为上游已经证明有效的能力。
- Headlong 固定提交 ca0b4017 的持续自主循环把外来消息当作观察，由模型选择何时回应。Rna 的项目理解循环独立于前台会话及 Goal，以新对话/执行结果/定期复查触发判断；模型选择 wait、work、share 或 learn，静音与输入避让只限制投递。无新信息时退避复查，不用持续空转伪造主动性。
- ASPIRE 的自建验证不能推出外部目标能力提升，参见 论文核对笔记。Rna 把能力包演进和评测标准演进分开，候选不能用自己新写的标准给本次晋升评分。

上游本地入口：Pi loop、Harness runner、Harness presets、Headlong。Rna SDK 不导入 Pi SDK。

## 项目初始化

真实项目创建后进入 queued → initializing → ready，或 failed/blocked/paused。模型输入包括用户标题、描述、实际能力目录，迁移时还有已有事实与约定；输出必须通过 schema、分配合法性及生成脚本执行检查。

一个能力包包含系统提示词、技能正文与资料、带 JSON Schema 的自动化脚本、评估条件及至少三个具体用例。脚本拥有 read/write/exec 权限声明，当前执行 API 为 input 与 api.readFile/writeFile/listFiles，不是任意 shell。它可生成与项目有关的产物或脚本；需要主机命令时使用用户已授予的 project_exec。

生成不是完成：初始事实明确标注模型推断，未执行的构建、测试与部署不能写成已完成。只有所有检查成功、能力文件提交并且项目仍存在且输入未变化时，才能一次持久化发布 baseline。失败不会产生半套已启用技能。原对话、事实、约定和旧版本保留。

新建项目未指定目录时使用独立目录，避免把 daemon 源码目录误当成用户游戏工作区。显式目录保留用户选择。

## 不可变版本与运行

每个版本保存 namespace、内容 hash、父版本及文件列表，落盘 SYSTEM.md、skills、tools、evaluation.json、genome.json。修改必须产生新版本，加载前验证文件与 hash；直接改已发布文件将拒绝运行。

前台轮次在第一次进入运行器前持久化所选版本 ID，暂停、进程重启与恢复仍使用该 ID。试用、采用、退出试用和回退到已采用版本的父版本都不改写在途轮次。技能按需加载；本轮只使用该版本的生成能力，避免混合旧提示词与新工具。外部技能/MCP/工具分配仍可在后续请求边界刷新。

后台研究只注入 read 工具；模型表达想要某能力不构成授权。后台进化在临时目录执行生成代码与评测，不修改用户工作区。生成脚本使用新的无凭据 Node 子进程、超时、输出上限及文件作用域；Node VM 不是系统安全隔离，整个本机控制面仍面向可信单用户。不能把它当成运行敌意代码的容器边界。

## 进化与评估

1. 根据项目证据提出完整候选，保留变化假设；提案上下文不包含基线评测案例与 smoke 的预期输出。
2. 保存基线能力包与冻结评测套件的 hash，再物化候选。
3. 实际运行候选脚本自己的 smoke 和基线工具的冻结契约样本。
4. 在独立临时目录分别用基线和候选执行相同案例，记录模型响应、工具参数、工具结果、失败与实际用量。
5. 校验必要词、禁止词、必需工具成功调用、完整结束与无不确定副作用。独立评分请求随机交换两侧顺序，只看到任务、冻结条件和匿名执行证据，不看到候选自评或新标准。
6. 检查改善阈值、退步阈值、最低质量、token 比例、脚本检查等全部条件；只有全部通过才 ready，其他保留 rejected/failed/interrupted/stale 与原因。
7. 主动循环依据真实结果决定何时邀请用户试用。只有经评估的版本能试用与采用；试用结束前不生成下一代，避免父版本不明确。

用户可在项目版本页编辑完整能力包（含评估标准），或 CLI 导出 JSON 后提交。编辑走同一评测器；新标准保留在候选中，本次仍按旧标准评分。一次通过仅表示在当前有限用例中通过门槛：评分器可使用同一个配置模型的独立请求，并非独立人类或外部保留集，也没有统计显著性保证。后续真实失败需要版本化扩展案例和重新验证，不能宣传为普适能力提高。

旧工具的 smoke 预期在当前通道中也是兼容契约。已发布不等于语义正确：正确但改变旧输出的修复也可能被拒绝。保留旧工具并增加新 ID 是一种兼容迁移方式，但若旧评测本身要求错误行为，仍须独立审查和修订标准。当前没有自动改写已发布预期、绕过门槛的破坏性迁移通道；候选不得为通过检查无意义地调用旧工具。

异常、取消、归档、急停、模型失败或基线改变都不能发布 ready；重启不自动重放未完成的付费进化。原始评测 trace 与失败报告保留用于检查。

## 三种 token 数值

- contextWindow：模型实际上下文能力，包含请求/响应所需空间；配置有明确来源，未知自定义模型必须填写。
- modelMaxOutputTokens 与 maxOutputTokens：模型输出能力上限与用户选择的单次输出上限，后者可更小。
- realTokenBudget：用户可选每日真实调用硬限，默认 null。真实用量独立记账，预留避免并发透支，缺失提供商报量时记估算。演示 token/USD 不影响真实模型；历史混合账本原样归档，不能伪造精确拆分。

供应商规格与复核日期见 模型目录来源。
